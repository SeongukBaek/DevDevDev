# 테스트 어려운 코드
- 하드 코딩된 파일 경로, IP 주소, 포트 번호 등
- 의존 객체를 직접 생성
- 정적 메소드 사용(정적 메소드가 다른 서버와 통신하는 경우 등), final 클래스나 메소드인 경우(대역으로 대체가 어려울 수 있음)
- 실행 시점에 따라 달라지는 결과(실행 시간을 활용하거나, Random 값을 활용하는 로직의 경우)
- 역할이 섞인 코드(로직이 여러 역할을 수행하는 경우)

# 테스트 가능한 설계
위 코드들의 테스트가 어려운 주된 이유: **의존하는 코드의 대체 수단이 없다.**

## 하드 코딩된 상수를 생성자나 메소드 파라미터로 받기
- 즉, 테스트 환경에 따라 경로를 다르게 줄 수 있도록 하기
- Setter를 추가하거나, 메소드 파라미터를 받도록 변경

## 의존 대상을 주입 받기
- 생성자나 Setter를 주입 수단으로 하여, 의존 대상을 주입받을 수 있도록 한다. 따라서 테스트 시에는 대역을 활용할 수 있도록 한다.

## 테스트하고 싶은 코드를 분리하기
역할이 섞여 있는 코드를 분리하는 것.
- 따라서 테스트할 코드에 대해서만 테스트할 수 있도록 한다.
- 하지만 해당 방식은, 오히려 코드에 대한 리팩토링이 필요해져서 코드 양이 많거나 불확실한 경우, 오버헤드일 수도 있겠다.

## 시간이나 임의 값 생성 기능 분리하기
시점에 따라 결과가 달라지는 경우에 대해, 해당 기능을 별도의 클래스로 분리해서, 테스트 시에도 해당 클래스를 통해 원하는 테스트 시점을 지정할 수 있도록 한다.

## 외부 라이브러리를 감싸서 사용하기
테스트 대상이 사용하는 외부 라이브러리를 대체할 수 없는 경우, 해당 라이브러리를 연동하는 클래스를 생성한다.
- ex. 외부 인증 API를 호출하는 `AuthUtil` 을 사용하는 코드는, `AuthSerivce` 라는 클래스로 감싸서 사용
- 테스트 시에는, 해당 클래스를 대역으로 대체해 테스트 가능
- 의존하는 대상이 final 클래스 또는 메소드인 경우도 동일하게 감싸는 클래스를 생성해 대역 테스트 가능
